# Detector-policy v1: published closed interface

Generated by `benchmarks/build_detector_contract.py`. This is documentation, **not a runtime manifest**.

## Deliberate boundary (audit F-03)

The Python registry is intentionally closed for baseline IDs, typed schemas, executor implementations and supported stage/phase ordering. YAML is authoritative **within that interface**, not an unrestricted detector/plugin language. Moving a list into YAML alone would not make the existing typed parsers, baseline accessors or scheduler generic.

YAML owns enablement, supported predicates/vocabulary, input and correlation fields, windows, thresholds, signal names/values, confidence, evidence and ATT&CK attribution. Weights own contributions. Python also retains structural invariants such as typed-emission maximum merge and dependency ordering. This contract does not move behavioural defaults back into code.

There are **35 required baseline IDs**. `rules_evidence_calibrated_v24.yaml` configures **44 detectors**, including **9 optional additional IDs**. These counts are not numbers of ATT&CK techniques or behavioural rules. The audit's “36 required” count is not the current parser contract.

## Required baseline bindings

Required IDs cannot be omitted, renamed or reassigned to a different executor/stage. Disable a detector with `enabled: false`, retaining its complete schema and satisfying live-producer dependencies. Disabled definitions still undergo validation.

`reserved_baseline` means dedicated parser binding code; some such bindings still use generic implementations. `required_generic` means a mandatory instance of a generic executor. Neither classification establishes maliciousness or active detection.

## Additional IDs without engine changes

A new non-reserved ID may use only these families. Provide a complete typed definition, unique signal/explanation ownership, weights, valid earlier-phase inputs and (for catalogue-enabled policy) mapped or explicitly unmapped ATT&CK annotations. Fixed baseline IDs remain present. No arbitrary Python callable, import path, evaluation string or plugin loading is accepted.

| Executor family | Supported stages |
|---|---|
| `qualified_artifact_command` | contextual |
| `signal_gate` | atomic, contextual |
| `signal_projection` | contextual, temporal |
| `signal_sequence` | temporal |

Gates run at phase10/30 (atomic/contextual), projections at29/45 (contextual/temporal), sequences at40 and qualified artefact commands at38. Same-phase, backward and unavailable-producer dependencies are rejected. See [the rule language](RULE_LANGUAGE.md) for full schemas and [Linux tool scoring](LINUX_TOOL_SCORING.md#bounded-linkage-contract) for qualified artefact commands.

`ordered_row_rules`, `ordered_signal_adjustments` and `grouped_signal_window` are reusable internally but not open additional-ID families. Existing policy can add supported branches/emissions within their required owning definitions; this does not permit a second executor instance under a new ID.

## Change and compatibility policy

A new executor implementation, baseline binding, arbitrary additional specialized instance or scheduler change requires an engine/API change with parser, dependency/field planning, sparse execution, carry/history, explanation and compatibility tests. Editing a registry document cannot implement those mechanics. Breaking interface changes should receive a new detector-policy contract version and migration guidance.

The published JSON snapshot is `docs/detector-policy-v1.json`. Verify documentation against the actual parser and current CLI policy:

```sh
python benchmarks/build_detector_contract.py --check
```

After deliberately reviewing an interface or example-policy change, regenerate without `--check` and run `tests/test_detector_contract.py`. The checker has no effect on production configuration, scores or execution. F-03 is addressed through the documented-intentional-contract option, **not** by making the registry open or YAML-driven.
