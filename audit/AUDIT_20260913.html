METHOD

What was actually checked

Every finding below rests on something executed, not read. Grep alone cannot distinguish a policy key name from an indicator literal, so the hard-coded-rule question was answered with an AST pass over the module rather than pattern matching.

  • Full test suite under uv with the declared dependency floor (pandas>=2.2), not the sibling .venv.
  • An AST scan of all 551 string comparisons and every numeric threshold comparison in the engine.
  • A cross-reference of all 434 YAML signal names against every string literal in the Python.
  • Engine construction and an end-to-end apply() run over synthetic Plaso-shaped frames at 2k / 10k / 40k rows, with cProfile.
  • Micro-benchmarks isolating the sparse-attrs effect and the string-backend effect.
  • Mutation tests against the shipped policy to establish what YAML can and cannot change.
PART i

Performance

The memory work described in docs/PERFORMANCE.md is genuine, carefully caveated, and correctly implemented. The audit initially concluded that the remaining opportunity was CPU — that the hot path still ran Python-level string code. That conclusion did not survive review; see the note below the profile and F-04.

The sparse-attrs optimisation is real, and larger than documented

The document reports that a scalar df.iat[row, col] read can recursively copy a partition's entire nested signal and explanation maps when chronosift_sparse is attached to df.attrs. I reproduced this in isolation, and it is dramatically worse than the write-up suggests:

4,000 reads · detached 48 ms 20k-row sparse payload
Same 4,000 reads · attached 8m 50s 529,534 ms
Penalty avoided 11,009× and it grows with payload size

The penalty is not a fixed multiplier — it scales with the size of the attached maps, because each read deep-copies the whole structure. At a 3,000-row payload the same experiment measures 1,417×; at 20,000 rows it reaches 11,009×. On a real partition the factor would be larger still, which is why this optimisation is load-bearing rather than incremental. Writes are unaffected at both scales (70.8 ms vs 70.5 ms).

I traced every stage that could be exposed. All six contextual stages carry @_without_sparse_state_attrs, and the row-loop detectors beneath them (_apply_impossible_travel_sparse, _apply_geo_continuity_sparse, _apply_file_lifecycle_signals_sparse) inherit the detached scope from their decorated parents. There are no scalar reads left in the engine at all — all twelve .iat sites are writes, and writes are unaffected. This optimisation is complete, and it is the single highest-value piece of the performance work.

The placeholder-column work is also verified

After ensure_required_fields, a frame carries 320 columns of null[pyarrow] and only 7 of object. The compact-null representation described in the September 10 notes is doing exactly what is claimed: wholly-absent fields cost no per-row value buffers.

Where the time goes — and what that profile does not establish

Profiling a 10,000-row apply() run (20.8 s total) put roughly a quarter of runtime inside pandas' object-array string path, with 3,014,177 re.Pattern.search calls and 4,869,184 str.strip calls.

This profile was taken on pandas 2.3.3 and does not describe the current engine It ran under the then-declared pandas>=2.2 floor, where the string dtype defaults to Python storage. The project floor is now pandas 3.0.3, where .astype("string") already yields Arrow-backed storage — so the engine's many existing .astype("string") helpers were never on the Python path in a supported install. An object input dtype also does not prove the subsequent regex executes in Python, and some patterns and flags require pandas' fallback regardless of storage. See F-04.

Scaling is clean

Throughput held at 1,007 → 1,237 → 1,264 rows/s across 2k / 10k / 40k rows, so cost is linear in row count with no super-linear blow-up. The row-wise detectors are genuinely sequential state machines (per-key continuity, sliding windows) and use two-pointer scans rather than nested passes — the right structure. Absolute throughput is modest, though: at ~1,250 rows/s the 21.4M-row corpus referenced in the performance notes is a multi-hour pass. That makes throughput worth continued attention — but on evidence gathered at the engine's real operation boundaries, which this audit did not produce.

PART ii

Hard-coded rules and ATT&CK linkage

On the first half of this question the codebase is in excellent shape. I went looking for static detection strings in the engine and did not find them. On the second half — everything tracing back to MITRE ATT&CK — the picture is much weaker than the documentation implies.

No hard-coded detection content survives in the engine

  • CLEAR Zero attacker indicators as literals. A targeted sweep for the obvious content — mimikatz, psexec, rundll32, certutil, lsass, ntds.dit, /etc/shadow, .aspx and thirty more — returns only policy key names such as "webshell_artifact". No process name, path, extension or registry key is embedded in the Python.
  • CLEAR 31 module-level constants, all structural. Regexes for IPv4/IPv6 shape, Parquet column names, manifest schema versions. Nothing that encodes a detection decision.
  • CLEAR 3 numeric literals in threshold comparisons, and all three are structural bounds — an IPv6 prefix maximum of 128, and evidence-size caps of 256 items / 16,384 characters. No scoring threshold is hard-coded.
  • CLEAR No YAML signal name is hard-coded. Names like short_lived_file do appear in the Python, but as semantic slots: the engine says emit(row, "short_lived_file", …) and YAML supplies the actual name, value, rule_id and confidence. I confirmed the indirection in the shipped policy. They coincide only by convention.
  • CLEAR The engine actively rejects regression. Loading a config with engine_config.path_taxonomy, detection_vocabulary, detection_event_ids or detection_thresholds raises — these are named as obsolete shared rule-logic sections. That is a migration away from hard-coded rules being enforced in code.

What the engine does own is a fixed vocabulary: executor names, operator names (contains_any, equals_any, regex…), resolver names, and emission slots. That is the correct division for a policy interpreter, and it is applied consistently. The detection content — tokens, paths, regexes, thresholds, weights — lives in YAML.

The detector catalogue, however, is a closed Python registry

chronoSIFT_v2_31.py hard-codes 35 detector IDs that must be present in detector_policy.detectors, and lines 12596–12634 pin their executors and stages. I tested what a policy author can actually change:

Operation on the shipped policyResultEngine response
Remove mft_timestomping REFUSED missing required key(s): mft_timestomping
Rename a required detector REFUSED same — the ID is the contract
Set enabled: false ACCEPTED registry satisfied by presence
Add a new detector ID ACCEPTED* *only signal_gate, signal_sequence, signal_projection, qualified_artifact_command
Change a required detector's executor REFUSED required canonical execution detectors must use 'signal_gate'

This reads as deliberate fail-closed design rather than oversight, and the enabled: false escape hatch means nothing is truly stuck. It is worth stating plainly all the same: the taxonomy of what ChronoSIFT detects is defined in Python, and the 24 specialised executors are each reserved to one fixed detector ID, so a new detector can only be built from the four generic ones. (This is now published as a contract — see the resolution under F-03.)

The ATT&CK requirement is not met — as audited, rules v23

The stated goal is that everything links back to MITRE ATT&CK. In the policy as audited, almost nothing did — in any machine-readable sense. This section records the state that prompted F-02; see its resolution for what rules v24 and attack_metadata.py now do instead.

Signal emissions 186 every one carries name, value, rule_id, confidence
… with a technique ID 0 no emission has an ATT&CK field at all
Techniques in structured fields 16 ClamAV behaviour + web mappings only
Techniques in prose only 36 95 references, all inside description:

The direct_attack_semantics detector illustrates the pattern exactly. Its rule content is properly YAML-owned — path_lower ends_with_any ["/authorized_keys"] — but its ATT&CK reference sits in the human-readable description string: 

id:          windows_log_cleared
description: "Windows event-log clearing recorded; intent and
              actor remain separate (ATT&CK T1685.005)"

A technique ID inside a sentence cannot be validated, cannot be emitted into the output frame, cannot be queried, and cannot be used to answer "which techniques does this corpus show evidence of?" — which is the question an ATT&CK mapping exists to answer. 32 of the 36 prose-referenced techniques never appear in a structured field anywhere.

The documentation compounds this. docs/ATTACK_MATRIX.md mentions 96 technique IDs, of which 47 appear nowhere in the shipped rules, and it cites the v10/v8 baseline YAML — thirteen rule generations behind the v23/v21 pair the CLI actually loads. The file is candid that it is "the historical implementation matrix," but it is the artefact a reader will treat as the coverage claim.

The mechanism already exists — it is just not applied

The engine already parses and validates a real technique field. At chronoSIFT_v2_31.py:8151 it enforces re.fullmatch(r"T\d{4}(?:\.\d{3})?", technique_id) on web-mapping outputs, and it already unions technique sets into a chronosift_attack_techniques output column. Extending _parse_named_policy_emissions and _parse_policy_emission to accept the same field would put all 186 emissions on that path without new machinery.

Two gaps would remain once it is wired up: nothing pins an ATT&CK catalogue version, and the regex validates shape only — a revoked, deprecated or mistyped ID passes. A pinned technique list checked at policy-load time would close both.

Findings

F-01 Critical Closed

Forensic events are silently dropped on the declared pandas floor

jsonl_to_parquet_cli_logging.py:174 · chronoSIFT_v2_31.py:27604 · chronoSIFT_v2_31.py:27755

Both ingest paths build timestamps with pd.to_datetime(series, unit="us", errors="coerce", utc=True) and then dropna(subset=["datetime"]). The comment above the engine's copy states that datetime64[us] "can represent forensic timestamps far beyond year 32767" — but microsecond resolution is only the default on pandas 3.x. On pandas 2.x the call returns datetime64[ns], anything outside 1677–2262 coerces to NaT, and the very next line deletes those rows.

pyproject.toml declares pandas>=2.2, so a conformant install loses data. I confirmed both sides: on pandas 2.3.3 a record at year 44567 is dropped; on pandas 3.0.3 it is preserved. This is also the sole cause of both test failures — the suite is correctly detecting a real bug, and it passes only on the sibling .venv because that happens to carry pandas 3.0.3.

Out-of-range timestamps are not noise in this domain. Corrupted, zeroed and deliberately tampered records are exactly the artefacts an examiner needs to see, and they are the ones being discarded without a warning.

Fix — verified working on pandas 2.3.3 Build the array at microsecond resolution directly instead of relying on to_datetime unit inference: 
dt = pd.Series(
    df["timestamp"].to_numpy().astype("datetime64[us]"),
    index=df.index,
).dt.tz_localize("UTC")
Alternatively raise the floor to pandas>=3 in pyproject.toml — but the portable fix is preferable, and either way a dropped-row count should be logged rather than discarded in silence.
Resolved — verified on the current tree

Closed by raising the floor rather than by the portable conversion. pyproject.toml now pins pandas>=3.0.3, and both the engine and the standalone ingest CLI carry an import guard that refuses to load on anything older, naming silent timestamp loss as the reason. Because the ingest path is a separate entry point that never imports the engine, guarding it independently is the right call — a floor in metadata alone would not have covered someone running that script directly.

Both previously failing tests now pass, and the full suite is green on pandas 3.0.5.

F-02 High Closed

ATT&CK linkage is documentation, not data

rules_evidence_calibrated_v23.yaml · docs/ATTACK_MATRIX.md

Covered in full in Part ii. In short: 0 of 186 emissions carry a technique ID, 36 techniques exist only inside description: prose, and the documented matrix references 47 techniques absent from the shipped rules while citing rule files thirteen generations stale. For a project whose stated purpose is dead-box ATT&CK coverage, the mapping should be a validated field on every emission.

Fix Add an optional attack_ids list to the emission schema in _parse_named_policy_emissions and _parse_policy_emission, reusing the existing T\d{4}(?:\.\d{3})? validation; migrate the 95 prose references into it; pin an ATT&CK catalogue version and check IDs against it at load time; then regenerate ATTACK_MATRIX.md from the policy rather than maintaining it by hand.
Resolved — substantially beyond what was recommended

A new attack_metadata.py module makes the mapping real data. The Enterprise ATT&CK 19.2 catalogue (858 techniques) is bundled under chronosift_data/ with its licence and verified by SHA-256 at load; all 285 policy producers now carry an annotation — 140 mapped, 145 explicitly unmapped — and every ID is checked against that catalogue rather than a shape regex.

Three things go past the recommendation. Revoked and deprecated IDs require a documented legacy_ids review, and an unused exception is also an error, so the list cannot rot in either direction. An attack_basis taxonomy separates observed behaviour from attempted behaviour, artefact capability and contextual inference, which keeps the evidential claim honest at the point of mapping. And validate_typed_refs cross-checks the parsed policy objects against the inventory, so a mapping that no parser reads is rejected.

I confirmed it end to end: technique IDs and basis are inlined into explanations at materialisation (T1021.004, T1133, T1098.004 in my run), a _chronosift_attack_metadata.json run manifest carries a mapping_sha256 provenance hash, and ATTACK_MATRIX_CURRENT.md is generated from the policy with a test asserting the checked-in copy matches regeneration — so the doc drift that made the old matrix misleading cannot recur. A consistency sweep over all 285 producers found no contradictions between basis, IDs and source.

F-03 Medium Closed

Detector taxonomy is a closed registry in Python

chronoSIFT_v2_31.py — required_detector_ids / specialised_detector_ids

35 detector IDs are required by name and pinned to specific executors and stages. New detectors are restricted to four generic executors. Mitigated by enabled: false, and defensible as a fail-closed contract — but it means the answer to "what does ChronoSIFT detect?" is partly in the engine, not the policy, which sits awkwardly beside the project's own stated principle.

Suggestion If the contract is intentional, say so in docs/RULE_LANGUAGE.md and name the 35 IDs there as a published interface. If it is transitional, move the registry into a YAML manifest the engine validates against.
Resolved — published as an interface

Taken as the first of the two options offered: the contract is now documented in docs/DETECTOR_POLICY_CONTRACT.md and referenced from RULE_LANGUAGE.md, naming the required IDs, the optional additions and the four permitted executor families. The registry stays in Python, which is a defensible choice now that it is a stated interface rather than an implicit one.

F-04 Medium Closed

Explicit Arrow text storage

chronoSIFT_v2_31.py — _prepare_arrow_text_columns(), called after enrichment

The audit recommended casting the normalised text columns to Arrow-backed storage after normalisation and before the detector stages. That change is implemented and validated. _prepare_arrow_text_columns() selects Arrow storage per column once enrichment is complete, admitting only columns that infer as text over all non-null values, leaving mixed, numeric, nested and compact-null columns intact, reusing existing Arrow buffers, and retaining original storage with a warning where Arrow cannot encode malformed Unicode.

Two errors in how this audit justified the finding

The diagnostic measured the wrong stage. The audit reported that text columns are object dtype based on a frame inspected after ensure_required_fields() — which runs well before the conversion point. It was a pre-conversion snapshot presented as the detection-stage state.

The benchmark ran on the wrong pandas. The 4.5× and 6.2× kernel ratios were measured on pandas 2.3.3, where string defaults to Python storage. On the project's actual floor of pandas 3.0.3 the default is already Arrow, so the engine's existing .astype("string") helpers were never on the Python path in a supported install. An object input dtype also does not establish that the following regex executes in Python, and some patterns and flags require pandas' fallback whatever the storage is.

Those ratios describe isolated operations, not engine acceleration, and this report should not have presented them as available headroom.

Resolved — with the benefit correctly attributed

Measured on the engine, the change is a memory optimisation, not a speed one: runtime is flat at 20,000 events (11.238 s → 11.213 s) and slightly worse in a single 50,000-event fresh-process pair, while peak RSS falls about 10.7% and pandas deep frame accounting about 41%. Validation covers eleven new tests for type admission, Unicode, regex compatibility, malformed text, nulls and buffer reuse, an AST check confining the diff to the new helper and its one call site, and independent pre/post replays showing every output column, score, signal, explanation and ID equal.

What remains is a genuinely open profiling question rather than a known bottleneck: re-profile the current engine at the real operation boundaries, on pandas 3, to find whatever avoidable Python work is actually left. This audit's dtype diagnostic does not identify it.

F-05 Low Closed

Shipped policy version is ahead of every document that describes it

run_chronosift_sidecar_cli.py:22–23 · rules/README.md:9 · CHANGELOG.md

The CLI defaults to rules_evidence_calibrated_v23.yaml and weights_evidence_calibrated_v21.yaml. rules/README.md states the runner defaults to v21 rules and v19 weights. The changelog's "Unreleased" section documents v21/v19 as the newest work and never mentions v22 or v23 at all — two rule generations shipped without an entry. For a research artefact where reproducibility is the point, the version a reader reconstructs from the docs is not the one the tool runs.

Resolved

The tree has moved to rules v24, and rules/README.md and the CLI default now agree. More durably, the ATT&CK matrix is no longer hand-maintained — it is generated by benchmarks/build_attack_metadata_policy.py and a test fails if the committed copy drifts from what the policy would produce.

F-06 Low Closed

GeoIP failures are indistinguishable from GeoIP misses

chronoSIFT_v2_31.py:1468 · :1475

Both the city and ASN lookups wrap the reader call in except Exception: pass. An address genuinely absent from the database and a corrupt, truncated or wrong-format .mmdb produce the same empty result, so geographic continuity and impossible-travel detection can degrade to silence across an entire run with no signal to the examiner. Most of the other 49 broad handlers in the engine are narrow parse guards and are fine; these two gate a detection input.

Suggestion Catch geoip2.errors.AddressNotFoundError for the expected miss and let anything else surface — or at minimum count and report reader failures in the run telemetry that already exists.
Resolved

Both the city and ASN lookups now catch geoip2.errors.AddressNotFoundError specifically, so a genuine miss leaves that database's outputs empty while any other reader failure surfaces instead of being mistaken for an absent address.

F-07 Info Closed

The whole-frame apply() API has no direct test

chronoSIFT_v2_31.py:17808 · ensure_required_fields at :22476

Tests exercise apply_atomic and apply_contextual separately, never the 13-argument apply() that composes them. Severity is low precisely because the production partitioned path does not call it — but it is public, it is what an external consumer of the module would reach for first, and it worked correctly when I drove it end-to-end.

Resolved

SUMMARY

Where this leaves the work

The rules-versus-engine separation is the strongest part of this codebase and it should be stated without qualification: I went looking for hard-coded detection logic with an AST pass, a signal-name cross-reference and a threshold scan, and the engine came back clean on all three. The policy-interpreter architecture is real, consistently applied, and defended in code against regression. That is unusual, and it is the thing the project set out to achieve.

The performance work is likewise substantiated rather than asserted — the documentation is unusually careful about distinguishing measured results from estimates, and the one mechanism I isolated turned out to be understated rather than overstated.

Both of the findings that mattered have since been closed. F-01 was the urgent one — a dependency floor the project itself declared was causing silent evidence loss — and it is now fixed at both entry points. F-02 was the structural one, and the response went well past the recommendation: a bundled, checksum-verified ATT&CK catalogue, every producer annotated and validated against it, retired IDs requiring documented review, an evidential-basis taxonomy, and a generated matrix that a test keeps honest. That is a stronger position than the original report asked for.

F-04 closed differently from the rest, and the correction is worth stating plainly. The storage conversion the audit recommended was already implemented and validated; what the audit got wrong was the justification. Its dtype diagnostic stopped before the conversion stage, and its 4.5×/6.2× figures came from isolated kernels on pandas 2.3.3 rather than from the engine on its actual floor. On the engine the change buys memory — about 10.7% lower peak RSS — and no speed.

That leaves string-path optimisation as an open profiling question rather than a known bottleneck. Establishing whether avoidable Python work remains means re-profiling the current engine at the real operation boundaries under pandas 3. Nothing in this report identifies it, and the earlier version of this section implied otherwise.
